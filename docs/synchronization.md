<h3>Synchronization</h3>

Synchronization is the final stage of **gd-Pipeline**

Transformation stage which every tracked level individually inside SQLite, but synchronization generates a consolidated data intended for visualization.

The synchronization pipeline performs two operations:

- Aggregate linked levels into a single logical progression.
- Export the aggregated data into a dedicated worksheet inside an existing Google Sheets spreadsheet.

---

## Aggregation

### Overview

SQLite stores every tracked level independently. Synchronization reads every stored level and produces a new data where linked levels become a single logical record.

Notes:
- Unlinked levels are exported without modification.

- The aggregation process does not modifies SQLite.

---

## Unlinked Levels

Levels without a `master_level_id` do not require aggregation, so synchronization simply send their information into the exported data while discarding fields that are only meaningful inside SQLite.

The following fields are omitted:

- canonical_id
- master_level_id
- attempts_synced

Every remaining field is exported directly.

### Note
There, we create a new field called `type`, it has the variant of the level, such as: `daily`, `gauntlet`, `online`, `editor`, `local`.
---

## Linked Levels

Levels sharing the same `master_level_id` are aggregated into one logical progression.

Each exported record follows the rules below.

| Field | Aggregation Rule |
|--------|------------------|
| level_id | `master_level_id` without variant suffixes (`-daily`, `-gauntlet`). Editor and Local IDs are preserved. |
| level_name | Name of the level. |
| level_type | Type of the level. (`daily`, `gauntlet`, `online`, `editor`, `local`)|
| difficulty | Difficulty of the level (check **docs/data_dictionary** difficulty field for more information) |
| completed | Every linked level shares the same value due to synchronization. |
| completion_date | Earliest completion date among linked levels. |
| attempts | Sum of every linked level. |
| tracked_attempts | Sum of every linked level. |
| playtime | Special aggregation (see Playtime Aggregation). |
| current_best | Highest value among linked levels. |
| worst_fail | Highest value among linked levels. |

---

## Representative Level

Some fields cannot be aggregated mathematically. Instead, Synchronization chooses a **original level**.

The original level is defined as the level whose:

```text
level_id == master_level_id
```

This corresponds to the original level inside the linked group.

The original provides:

- level_name
- difficulty

This guarantees that exported metadata always represents the original level instead of one of its copies.

---

## Completion Synchronization

Completion status is synchronized across every linked level.

Whenever one level in a linked progression is completed, every linked level is marked as completed, but unlike the `completion`, the `completion_date` is **not synchronized** inside SQLite.

This is an intentional design decision.

### Why?

Geometry Dash does not expose the original completion date during initial scans.

As a result:

- Watchdog events can provide an exact completion date.
- Full scans cannot.

Synchronizing completion dates would overwrite valid historical information with unknown values, causing inconsistent progression records.

For this reason:

- `completed` is synchronized.
- `completion_date` always remains local to each tracked level.

During aggregation, synchronization selects the earliest available completion date among the linked levels for visualization purposes.

---

## Level Type

Unlike `level_name` and `difficulty`, the `level_type` field is not copied from the representative level. Instead, Synchronization analyzes every linked level and builds a consolidated type describing every progression path present in the linked group.

Each linked level contributes one type according to its `canonical_id`.

| Canonical ID | Type |
|---------------|------|
| `123456` | Online |
| `123456-daily` | Daily |
| `123456-gauntlet` | Gauntlet |
| `123456-local` | Local |
| `1540-editor` | Editor |

The final value is generated by joining every unique type using `/`.

### Double Types Examples

| Linked Levels | Exported Type |
|---------------|---------------|
| Online + Daily | `Online / Daily` |
| Online + Gauntlet | `Online / Gauntlet` |
| Online + Editor | `Online / Editor` |
| Local + Online | `Local / Online` |

This approach preserves every way the player has interacted with a linked progression while avoiding duplicated information.

## Playtime Aggregation

Playtime requires a different aggregation strategy.

Unlike Death Tracker, Playtime Tracker already merges every **online variant** of the same level into a single JSON file.

Examples include:

- Daily
- Weekly Demon
- Gauntlet
- Event

These variants therefore contain identical playtime values, so summing every linked level would duplicate the player's total playtime.

Synchronization prevents this by grouping linked levels according to their Geometry Dash `level_id`.

Rules:

- Levels sharing the same `level_id` contribute only once.
- Levels with different `level_id`s always contribute individually.

### Example

| Name | Type | level_id | playtime |
|------|-------|----------|---------:|
| Necropolis | Original | 2241592 | 259 |
| Necropolis | Daily | 2241592 | 259 |
| Necropolis copyable | Copy | 6839035 | 120 |

Exported playtime:

```text
259 + 120 = 379
```

The Daily variant is ignored because its playtime is already represented by the original level.

---

## Export Model

Synchronization converts SQLite records into a simplified export model.

Unlike `Level`, which represents the persistent database schema, the export model only contains information required for visualization.

fields:

- canonical_id (removed)
- master_level_id (removed)
- attempts_synced (removed)
- level_type (added)

The export model represents the player's logical progression rather than individual tracked files.

---

# Google Sheets

## Overview

Google Sheets is the visualization layer of **gd-Pipeline**.

Synchronization exports the aggregated data into a dedicated worksheet that serves as the data source for the rest of the spreadsheet, allowing users to build custom dashboards, statistics and formulas without modifying the synchronization process.

---

## GD Raw Data Worksheet

Synchronization writes every aggregated record into a worksheet named **GD Raw Data**.

This worksheet should be considered read-only.

---

## Update Strategy

During synchronization, gd-Pipeline rebuilds the **GD Raw Data** worksheet from SQLite.

The synchronization process performs the following steps:

1. Read every level stored in SQLite.
2. Aggregate linked progressions.
3. Generate the export dataset.
4. Clear the contents of the **Gd Raw Data** worksheet.
5. Insert the newly generated dataset.

Because SQLite remains the source of truth, rebuilding the worksheet guarantees that every exported statistic reflects the current database state.
